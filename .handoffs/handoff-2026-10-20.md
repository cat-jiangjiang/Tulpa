## 3. 关键结论

### A. 「监听着听着就不回了」：MCP 请求 id 去重

MCP 端点按 `(grant_id, JSON-RPC id)` 去重。客户端固定用 `id: 2` 调 `tools/call`，采集器长轮询占着 id=2 时，任何第二次调用都被判重复，返回 409 `{"error":"MCP request denied"}`。客户端误当授权失效 → 重新签发 grant → 会话绑定在旧 grant 上一起消失 → 群里留孤儿会话挡住新会话。

修法：每次调用取新 `next_id()`；只有 401 才续签，409 属并发去重不续签。`session.alive()` 还要看 `session.active`——已停止的会话仍能 `get_chat_session` 返回，否则采集器会对着 stopped 会话空转。

### B. watchdog 三次翻车

1. **无退避堆积**：探活失败即重启，10:50→13:14 攒出 147 个 `Threads=0` 的幽灵进程。只能重启系统清掉，`taskkill` 杀不动（EPROCESS 已终止，句柄没回收）。
2. **误杀忙碌实例**：14:53:20 单次探活失败就杀，而当时 NapCat 正在推 6 条消息（collector 14:53:21 就落盘了）。改为 HTTP 超时 10s→20s，且必须连续 3 次、跨 30 秒都失败才判死。
3. **把崩溃弹窗当健康**：崩溃的实例端口还在 LISTENING，但 OneBot 不应答。改为探 `get_login_info` 的真实返回，实测假活约 8 秒内能重新上线。

### C. 采集器落盘即 ack

旧代码每收到一批就等 agent 写 ack，这 120 秒内完全不监听，所以上一批刚结束时的 @ 要等两分钟才落盘。游标语义是「已入库」而非「已回复」，批次本身留在 `wg_events.jsonl` 不会丢，所以落盘即可推进。

### D. QQ 崩溃的三层，最后一层才是真因

1. 表象是 GPU 进程连续崩溃（`GPU process exited unexpectedly` ×6 → `FATAL: GPU process isn't usable`）。本机有两个虚拟显示器驱动（Meta Virtual Monitor、GameViewer Virtual Display Adapter），是常见诱因；`296c168` 用 `--disable-gpu` 绕开。
2. 中间层是崩溃上报永远写不完：QQNT 目录下**只有 `crashpad_handler.exe`，没有 `CrashSender.exe`**，所以每次崩溃都卡在「拉不起发送器」的模态框上，进程永不退出，桌面上的黑框就是它。
3. 真因是**代理沙箱注入的 `tsbx.dll`**。注入沿 `up.py → supervisor → watchdog → NapCatWinBootMain → QQ` 一路继承，QQ 约 20 秒后以 `0xC06D007F`（delay-load 的 `ERROR_PROC_NOT_FOUND`）自杀。最近 12 份 WER 崩溃报告的 `LoadedModule` 全部含该 DLL。

排除项：自写 PE 解析器验证 QQ.exe / QQNT.dll / 三个原生 `.node` 的延迟导入全部可解析，所以不是缺文件，是运行时 `GetProcAddress` 被 hook 破坏。沙箱配置也绕不过：正确 key 是 `sandbox.allowUnsandboxedCommands`，但 `app.asar` 的 `ensureHostEndpoint` 硬编码 `=false (product policy)`。

### E. 栈必须从 explorer 起

`start-bot.pyw` 是 `.pyw`（关联 `pythonw.exe`，无控制台），由 `explorer.exe` 代启动，父进程是 explorer，既不继承注入也不在代理的 job 对象里。

- `ShellExecuteW` 不行：对 .exe 内部仍走 `CreateProcess`，实测 `parent=python tsbx_count=1`。
- `.vbs` 不行：`explorer.exe x.vbs` 打开的是所在文件夹。
- 代理里直接起的 `DETACHED_PROCESS` 子进程连一行日志都写不出来就被杀；`schtasks.exe` / `cmd.exe` / `reg.exe` 都在沙箱黑名单里。

配套：`bootstrap.sandbox_dll()` 用 `GetModuleHandleW("tsbx.dll")` 自检，非 `--status-only` / `--allow-injected` 时直接 `exit 2`；`watchdog.py` 启动时若带注入会打 WARN；`up.py --stop` 用 `taskkill /F /T /PID` 退整栈。

### F. 监听只活一轮，必须重挂

`listen.py` 是唯一把「有人 @」变成「叫醒 agent」的进程，设计上 `WAKE` 就退出（让 agent 观察到完成事件）。会话中断 / 栈重启 / 上下文压缩后没人重挂，消息照落 `wg_events.jsonl` 但没人叫醒，表现为「发了消息没反应」。

`up.listener_pids()` 匹配 `daemon/listen.py`，`up.py --status` 直接显示「监听 : 未挂 —— 消息照收，但没人会叫醒你」。

### G. 按花名 @ 人

`reply.py` 新增：

- `AT_TOKEN = re.compile(r"@\{([^{}\n]{1,24})\}")`：只有写在花括号里的名字才算 @。群里正文的「@时月」是普通文字，真正的 @ 是消息段。
- `group_members(group_id)`：走 OneBot `get_group_member_list`，进程内 `_ROSTER` 记忆化。
- `resolve_member(name, group_id)` 四层解析，精确优先：纯数字当 QQ → 本群名片/昵称精确 → 档案（主名/别名）精确 → 本群名片近似 → 档案近似（单字不做近似）。

名片排在档案前面：群里最直白的称呼是名片（`时之锁-肠宝盒`、`坏乖😋`），档案兜住改名前的老叫法（`孩董` → criss、`领导` → 时月）。**同名报候选，不猜**：`--who momo` 列出 3 个 momo，`--who 时之` 列出两张撞车名片。解析失败降级成文字照发，不拒发。`@{🐟包}` 判为「是我自己」。

`build_segments()` 把 `@{花名}` 换成 at 段，`_tidy()` 合并相邻 text 段；带 at 段时**强制走 OneBot**（`send_chat_reply` 只吃纯文本，会把 at 静默降级成文字），OneBot 不可用直接 `SEND_FAILED`。

`memory_engine.find_profile` 拆出 `match_profiles()` 返回 `(exact, loose)` 全集；新增 `GENERIC_ALIASES = ("领导", "群友")`。

真实验证：回 `id=1516`，`get_msg` 回读 `[CQ:reply,id=1624835236][CQ:at,qq=843372773] 学废了`；回 `id=1533` 时 `@{孩董}` 走档案别名命中。

### H. 连发的 @ 被一条回复吞掉

事故：`1563`（「？」）和 `1564`（「@一下地牢主」）相隔 30 秒。回 1563 的那条消息落在 1564 之后，`up.replied_after` 的兜底规则「这条之后只要出现过自己的消息就算回过」把 1564 判成已回。于是 `--list` 显示 `[已回]`、`watch.py` 从 `fresh` 里滤掉，群里表现为「@ 了没反应」。

修法：`up.ledger_started()` 读 `wg_replied.jsonl` 首条 `ts`（按 mtime 缓存），`replied_after` 对**比它新**的事件只认账本，兜底仅对账本建立之前的老消息生效。回归测试 `scripts/check_wake_ledger.py`，四条断言。

配套：`reply.py --wait N` 发完就地进等待（`listen.py --timeout N --cycles 1 --no-digest`）；`--also ID` 一条回复顺带记多条账；发送前若发现还没回的唤醒（含更早的），打印 `NOTE 还有 N 条没回：<ids>`。

`--no-digest` 必须有：不加时超时会跑 `dossier.py --digest`，积压时实测 62 秒，把「等 6 秒」拖成一分钟。

### I. `--wait` 前台被超时砍掉

实测前台跑 `--wait 180`，工具超时把进程组 SIGTERM 掉；消息其实已经发出，但 stdout 走管道是块缓冲，连 `SENT` 一起被吞。修法：`sys.stdout.reconfigure(encoding="utf-8", line_buffering=True)`，规则里写明 `--wait` 要放后台跑。

### K. 推送通道：`git push` 在这个环境里不可用

代理对 `github.com` 回 `CONNECT tunnel failed, response 502`，`env -u HTTP_PROXY` 直连超时；但 `api.github.com` 是 200。SSH 通道是通的（443 和 22 都能连到 GitHub），但本机密钥没注册，注册要 `admin:public_key`，而 gh 令牌只有 `repo` 等范围。

所以改走 Git Data API 重放，脚本在 `.tmp/replay_push.py`（gitignore，不入库）：解析 `git cat-file commit` 原始字节 → 建 blob/tree（校验 tree SHA）→ 建 commit（校验 commit SHA）→ 全对才 `PATCH ref`。任何一步不一致就中止，不会写出脏历史。

踩过的坑：

- `gh api repos/X/git/commits/<短SHA>` 一律 404，**必须给完整 40 位**。
- `git log -1 --format=%B` 会在消息末尾**再加一个换行**（输出尾部 `0a0a`），而提交对象里只有一个 `0a`。多送一个字节，四个 SHA 全 DIFF。改用 `git cat-file commit` 的原始字节解析后全部逐字节一致。
- 顺带探测过：GitHub **原样保留** `+0800` 时区（API 回读显示成 `Z` 只是展示层），消息尾换行也保留。所以「API 重放做不到同 SHA」是误解。

`git fetch` 同样被挡，本地 `origin/main` 需手动 `git update-ref` 对齐。

### L. `--context`：回之前看得到群里在聊什么

`mention_only` 是服务端过滤的，闲聊根本不进 `wg_events.jsonl`，所以 Agent 手里只有「谁 @ 了我」，看不到前因后果。

`reply.py --context N [--around ID]` 直接读 `chat_inbox`——后端在决定要不要推送之前就把每条消息写进去了。输出标出「我」（自己说过的话）、「唤醒」（触发的那条）、「回这条」（`--around` 的目标）和「撤回」，跳过系统提示。

### N. 追问窗口：回复之后继续听群里聊

`mention_only` 让闲聊进不了 `wg_events.jsonl`，但 `chat_inbox` 里有**全部**消息——后端在决定要不要推送之前就已落库（`delivered=0` 的正是被滤掉的闲聊）。`reply.py` 发送成功后写 `.tmp/wg_followup.json` 开窗，`watch.py` 每轮顺带查一眼窗口之后的新消息：有群友接话就唤醒（行带 `[追问]` 前缀），接满 `max_messages`（默认 10）或静默超 `idle_seconds`（默认 180）就收窗。自己的话和系统提示只推进游标，不唤醒、不占额度。

**关键设计：不碰 collector。** 改 collector 的 `mention_only` 要等它当前这轮 170 秒长轮询返回才生效，开窗后的头几句必然漏掉；而 `collector` 继续只投递 @、追问读全量库，两条路径没有竞态。会话重建会让窗口失效关闭（`after_id` 指的是旧会话编号），这是故意的。

回追问消息时 `reply.py` 自动从 `chat_inbox` 兜底查群号和 `onebot_message_id`（`event_target` 先查流水再查库），原生引用挂得上去。`config.json` 的 `followup` 段调参，`--no-followup` 单次关闭，`followup.py --show` 调试。

### O. Windows 控制台两个怪癖

1. **无控制台父进程拉起控制台子进程，会凭空开一个新控制台**——这就是「启动的进程弹出黑色命令行」那件事。修法：每个 `subprocess` 都带 `creationflags=CREATE_NO_WINDOW`（`up.py` 早有，`reply.py --wait` 漏了）。
2. **新控制台默认 OEM 代码页 936**：脚本写 UTF-8，字节按 GBK 读出来就是乱码。`winconsole.use_utf8_console()` 在 `SetConsoleOutputCP(65001)` 可用时才调（无控制台/非 Windows 直接跳过）。

## 6. 项目约定

- 包管理器：Python 一律 `uv`，禁止 `pip`；Node 脚本零依赖直跑，确需依赖用 `pnpm`，禁止 `npm` / `yarn`。

- 进程安全：禁止 `taskkill /F /IM python.exe` 之类通配杀进程；宿主机官方 QQ 绝对不可终止；端口清理走 `netstat -ano` → `tasklist /FI "PID eq <pid>"` → `taskkill /F /PID`。
- 提交：约定式提交；`git add <file>` 逐个暂存，禁止 `git add .`；commit 前跑 `check_publication.py`。
- 隐私：`.env`、`water-group/config.json`、`water-group/status.json`、真实人设卡（`*yu_bao*`）、`data/`、`imports/`、`reports/`、`tools/`、`.workbuddy/` 均在 `.gitignore` 内。`.workbuddy/` 是 Agent 的逐日记忆，会写进真实群友 QQ 号，**永远不要入库**。

## 7. 操作指引

### 启动

```bash
# 唯一正确入口（后台跑，永不返回，输出看 water-group/logs/launcher.log）
.venv/Scripts/python.exe -c "import subprocess,pathlib; subprocess.Popen(['explorer.exe', str(pathlib.Path('water-group/start-bot.pyw').resolve())])"

# 只读复查
.venv/Scripts/python.exe water-group/daemon/up.py --status

# 停整栈（stop.ps1 只管 app.py，停不干净）
.venv/Scripts/python.exe water-group/daemon/up.py --stop
```

冷启动耗时参考：NapCat 注入约 65 秒，`app.py` 起端口约 20 秒，采集器建立会话约 20 秒。

**重启整栈前先确认端口真空**：`--stop` 只退 supervisor / 看护 / 注入实例，`app.py` 与 `collector.py` 常常原地活着占着 47860 / 48777；而启动器按端口判幂等，会直接认定「已在运行」退出。先 `netstat -ano | grep -E ":47860|:48777"`，有残留按 PID 精准清。

### 日常循环

```bash
# 挂监听（只活一轮，WAKE 后必须重挂）
.venv/Scripts/python.exe water-group/daemon/listen.py --timeout 300

# 看谁 @ 了我
.venv/Scripts/python.exe water-group/daemon/reply.py --list

# 回之前看群里在聊什么（含闲聊，不只是 @）
.venv/Scripts/python.exe water-group/daemon/reply.py --context 30
.venv/Scripts/python.exe water-group/daemon/reply.py --context 30 --around 1760

# 回一条（自动查消息编号 + OneBot 原生引用 + 写账本）
.venv/Scripts/python.exe water-group/daemon/reply.py <id> "<正文>"

# 带 @
.venv/Scripts/python.exe water-group/daemon/reply.py <id> "@{时月} 来一下"
.venv/Scripts/python.exe water-group/daemon/reply.py <id> "学废了" --at 班味鹅
.venv/Scripts/python.exe water-group/daemon/reply.py --who 时之锁

# 一波连发用一条答完
.venv/Scripts/python.exe water-group/daemon/reply.py <id> "<正文>" --also 1565 --also 1566

# 回完就地等（必须放后台跑）
.venv/Scripts/python.exe water-group/daemon/reply.py <id> "<正文>" --wait 240

# 追问窗口：回复成功会自动开窗；[追问] 前缀的唤醒照常回
.venv/Scripts/python.exe water-group/daemon/followup.py --show   # 当前窗口
.venv/Scripts/python.exe water-group/daemon/reply.py <id> "<正文>" --no-followup  # 单次关窗
```

唤醒行可能是 `[at]` / `[keyword:…]`（有人在叫你），也可能是 `[追问]`（你回复之后群里还在聊）。后者回完同样自动续窗。
